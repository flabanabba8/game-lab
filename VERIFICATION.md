# Verification

Version 0.5.0 of the bundle. Dated 2026-11-21, Linux only. Earlier version-specific results are retained below.

## 0.5.0 - Godot 4 importer for Game Localization Studio (2026-11-21)

New: `localize_inspect` accepts a Godot 4 `.pck` (GDPC format 2 or 3, unencrypted) and drafts Dialogue Manager line text and speaker names, strings in uncompressed binary scenes/resources, and String constants of compiled scripts; `localize_export` writes one new `.pck` (format 3). Strings that are both a scene/resource string and a script constant are blocked until `allow_name_matches`. Helpers for lossless-WebP `.ctex` textures. Pure Python; compiled scripts use the standard library `compression.zstd` (Python 3.14+). New wiki page `llmwiki/localization/godot.md`.

- **Tested (offline, Python 3.14, Linux):** 6 new tests in `tests/test_godot.py`, all passing, on a pack built in the test (no game files bundled): an unchanged repack keeps every entry's name, bytes and MD5; all carriers are found, title lines and `res://` paths are left out, and only text shared by a scene string and a script constant is blocked; BBCode/`{{variable}}` tokens must survive and single-line labels cannot gain line breaks; export leaves the source pack untouched, the new pack reads back, dialogue text and speaker change while `raw_text` stays, a lengthened scene string keeps the internal-resource offset pointing at its body, untouched entries are byte-identical, the compiled script repacks; texture decode/encode round-trips and refuses a size change; non-pack and encrypted packs are refused. `tests/test_unity.py` and `tests/test_studio.py` still pass (39 tests together).
- **Real files (2026-11-21), one game:** a commercial Godot 4.5.1 pack (2,940 entries) with a finished human-reviewed translation. Inspect, fill every unblocked unit from that translation by source text, validate (structural OK) and export took about 72 s and 0.7 GB. The exported pack changed 245 entries; in 62 of 65 dialogue files the player-visible text equals the separately built reference pack (the 3 others differ where the same source sentence was translated differently in different scenes, because the fill matched by source text). The exported pack boots headless on the official Godot 4.5.1 Linux build with 0 error lines. The original pack was not modified.
- **Not tested:** playing the plugin-exported pack (the reference build made with the project's own tools was played); compressed (RSCC) resources; format-2 export; Godot 4 games without Dialogue Manager; any second Godot game; a Hermes session using the tools. Translating a blocked string or one that a script compares by value can still break a game: check before allowing.

## 0.4.0 - Unity importer for Game Localization Studio (2026-11-17)

New: `localize_inspect` accepts a Unity game folder (Mono build, loose serialized files, format 22) and drafts the text in JSON text assets, script-component string fields and `Assembly-CSharp` string literals; `localize_export` writes patched copies; new tools `localize_units_file` and `localize_import_translations`. Pure Python, no new dependency. Version 0.3.2 to 0.4.0; 29 tools.

- **Tested (offline, Python 3.14, Linux):** 16 new tests in `tests/test_unity.py`, all passing. They build synthetic serialized files and a synthetic PE assembly in the test itself (no game files are bundled) and check: the object table reads and an unchanged rebuild is byte-identical; growing or shrinking one object moves the rest and keeps their alignment; other format versions, big-endian, truncated and UnityFS data are refused; JSON string values are addressed by path with their exact span and duplicate keys are refused; an `ldc.i4` operand that looks like an `ldstr` is not mistaken for one, also behind a `switch` and a two-byte opcode; text is found in all three carriers while font tables, non-JSON text assets and other object types are left out; a script class is resolved through an external file reference; name matches are blocked until allowed; placeholders and tags must survive; the export reads back, untouched objects are byte-identical, non-string fields around a changed component string are intact and the JSON differs from the original only in the changed values; the JSONL round trip saves good lines and reports bad ones by line; tampered stored sources refuse export; the game folder is unchanged after every test; RPG Maker drafts still work beside Unity ones.
- **Wider run:** 145 tests across every Python test file except `tests/test_clips.py`: 143 pass. The 2 that fail are ModLab tests this change does not touch (`test_real_cli_read_only_help`, `test_every_toolkit_call_is_put_to_the_user`); both fail the same way on the previous commit on this machine, where a `rea` executable and an answered ModLab interview are present. `tests/test_clips.py` and the Desktop page test were not run for this version.
- **Real files (2026-11-17), one game:** a Unity 6000.0.45f1 Windows Mono build. Inspect found 3,424 units in four files (1,926 in JSON text assets, 1,292 in components, 206 code literals), 181 of them blocked as name matches, in under 2 seconds. Every unblocked unit (3,243) was given a marker plus its own source text (a length-changing pseudo-translation, not a translation), imported from the JSONL file, validated and exported. The exported files were then read with two parsers that share no code with this plugin, UnityPy 1.25.4 and dnfile 0.18.0: the three serialized files load, object IDs and types equal the originals, 34,962 of 36,008 objects are byte-identical and the 1,046 that differ are exactly TextAsset and MonoBehaviour objects, the names of 12,241 other objects still read, and all 3,243 marked strings were found at their places (JSON values, length-prefixed component fields, the assembly's string heap); the assembly keeps its 3,844 methods and 627 types. The game folder was compared before and after: unchanged.
- **Not tested:** starting the patched game, on Windows or under Wine or Proton, so nothing here shows that it loads, that fonts have the needed letters, that text fits, or that no translated string was a lookup key. Any second Unity game or Unity version; files that carry type trees (the header reader skips them, untested on real data); files near the 256 MiB limit; IL2CPP games; a Hermes session using the new tools; the Desktop page with a Unity draft. No real translation was produced or reviewed.

## 0.3.2 - playtest clips of failed checks (2026-11-13)

New: `playtest_run` records the capture time of every saved evidence frame and, for each FAIL, writes a captioned H.264 MP4 into `<run id>-clips` beside the evidence (default 3 s before to 1.5 s after the check's last frame, capped to the run's first frame and end), plus one reel when there are two or more. New tool `playtest_clips` re-cuts, clips a check by name, or cuts from a recording the user made (path plus wall-clock start time; approval asked before the file is read). Caption bar drawn with Pillow (no ffmpeg drawtext needed). Version bumped 0.3.1 to 0.3.2.

- **Tested (offline, Hermes managed Python 3.11, disposable Hermes home, ffmpeg 8.0 and ffprobe on this machine):** 140 tests, all passing, 11 of them new in `tests/test_clips.py`, using generated PNG frames and ffmpeg lavfi videos. They check, with ffprobe: a failing check gets an H.264 yuv420p clip with even dimensions whose start, end and duration match the run's event times (within 0.25 s); the first picture is the frame that was on screen at the clip start; caps at the run's first frame and its end; several failures plus the reel in order; a passing or unverified run makes nothing (no folder); a passing check is clipped only when named; ffmpeg missing says so in the report and the report stays complete; hostile check names (path separators, shell characters, control and escape characters, very long non-Latin text) give plain `clip-NN-name.mp4` files inside the folder; evidence names edited in the saved run are rejected; a recording with a start-time offset is cut at the right second (checked by pixel colour); a recording outside the time range is skipped with a reason; bad or missing recording arguments are refused; `playtest_run` itself, with mocked capture, records frame times, makes the clip only for the FAIL, and `clips: {enabled: false}` makes none.
- **Real run (2026-11-13):** SuperTux 0.6.3 (the installed `supertux2`, level "Between Two Glaciers") on an owned Xvfb display (1280x720), driven by `playtest_run` through real xdotool and Pillow capture. One check, "Tux runs right", failed (changed 0.42 percent; no movement detected); the clip was cut (1280x862 H.264 yuv420p, 3.04 s, 4.0 s to 7.1 s of the run) and three frames from it were looked at: the check name, expected and seen lines and the "frames from the run" tag were readable and the game frame was in each. The game and the display were closed by PID afterwards. Honest caveats: the other check in that run, a jump, was reported PASS by the existing heuristic and an earlier run reported a wrong "walks down" PASS (the experimental limits above still apply); the clip is three frames about half a second apart, so it shows the failure moment, not what the game did in between.
- **Not tested:** cutting from a real screen-recorder file (only ffmpeg-generated test videos); recordings with variable frame rate, rotation or no duration; a Hermes session or the approval card for `playtest_clips`; any other game; Windows, macOS, Wayland-only; ffmpeg builds without libx264. Runs saved before 0.3.2 have no frame times and cannot be clipped. A recording whose start time is off gives a wrong moment.

## 0.3.0 (ModLab part) - scan, ask, never pick; and ModLab can no longer fill a disk (2026-11-12)

- Disk safety (a lab is a full copy of a game): ModLab now checks free space and its own total cap before writing every file, stops and removes its own partial work if a copy would pass the reserve (10 GB or 10 percent of the disk, whichever is larger) or the cap (default 25 GB), uses copy-on-write clones where the filesystem supports them (not on ext4, which this machine uses), keeps only the last 2 revisions of a lab, prunes toolkit output to 20 runs / 64 MB, removes unfinished lab folders left by a crash, and adds `modlab_cleanup` (report; dry-run-first deletion; only inside ModLab's own folder; only with confirm=true). Before this change every apply copied the whole game again, every revision was kept forever and the only guard was "free space at least twice the game". Settings: `modlab_max_total_gb`, `modlab_min_free_gb`, `modlab_keep_revisions`. A test fails the build if the shipped plugin grows big files or archives.
- New `modlab_setup`: scans the computer (installed modding tools, installed Steam games with duplicates, runtime components and unmounted libraries handled), identifies the engine and any anti-cheat of a chosen game folder by file signatures, lists the modding routes found for that engine with what each needs and what is missing, asks the user, and saves the route the user picked. ModLab never picks a route. `modlab_toolkit` and `modlab_create` return the interview until it is answered.
- New wiki `llmwiki/modding-routes.md` and `modding_catalog.json`: 12 engines, 18 routes, 39 tools, anti-cheat statements and upload rules, each with source and date (read 2026-11-12); RPG Maker, Creation Kit and several signatures are marked UNVERIFIED or "convention". Knowledge freshness: stale after 30 days or a passed deadline, and the plugin offers online research only if the user says yes; approved research is stored as dated overrides.
- Tested here: 121 Python tests. The engine scan was run on a real Steam library of 20 games on this machine and corrected three times from the result (nested game folders, Source 2 two levels deep, Godot with an embedded pack). Not tested: the game-folder scan on Windows or macOS, any loader install, or any mod run.

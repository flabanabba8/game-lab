# Verification

Version 0.3.2 of the bundle. Dated 2026-11-13, Linux only. Earlier version-specific results are retained below.

## 0.3.2 - playtest clips of failed checks (2026-11-13)

New: `playtest_run` records the capture time of every saved evidence frame and, for each FAIL, writes a captioned H.264 MP4 into `<run id>-clips` beside the evidence (default 3 s before to 1.5 s after the check's last frame, capped to the run's first frame and end), plus one reel when there are two or more. New tool `playtest_clips` re-cuts, clips a check by name, or cuts from a recording the user made (path plus wall-clock start time; approval asked before the file is read). Caption bar drawn with Pillow (no ffmpeg drawtext needed). Version bumped 0.3.1 to 0.3.2.

- **Tested (offline, Hermes managed Python 3.11, disposable Hermes home, ffmpeg 8.0 and ffprobe on this machine):** 140 tests, all passing, 11 of them new in `tests/test_clips.py`, using generated PNG frames and ffmpeg lavfi videos. They check, with ffprobe: a failing check gets an H.264 yuv420p clip with even dimensions whose start, end and duration match the run's event times (within 0.25 s); the first picture is the frame that was on screen at the clip start; caps at the run's first frame and its end; several failures plus the reel in order; a passing or unverified run makes nothing (no folder); a passing check is clipped only when named; ffmpeg missing says so in the report and the report stays complete; hostile check names (path separators, shell characters, control and escape characters, very long non-Latin text) give plain `clip-NN-name.mp4` files inside the folder; evidence names edited in the saved run are rejected; a recording with a start-time offset is cut at the right second (checked by pixel colour); a recording outside the time range is skipped with a reason; bad or missing recording arguments are refused; `playtest_run` itself, with mocked capture, records frame times, makes the clip only for the FAIL, and `clips: {enabled: false}` makes none.
- **Real run (2026-11-13):** SuperTux 0.6.3 (the installed `supertux2`, level "Between Two Glaciers") on an owned Xvfb display (1280x720), driven by `playtest_run` through real xdotool and Pillow capture. One check, "Tux runs right", failed (changed 0.42 percent; no movement detected); the clip was cut (1280x862 H.264 yuv420p, 3.04 s, 4.0 s to 7.1 s of the run) and three frames from it were looked at: the check name, expected and seen lines and the "frames from the run" tag were readable and the game frame was in each. The game and the display were closed by PID afterwards. Honest caveats: the other check in that run, a jump, was reported PASS by the existing heuristic and an earlier run reported a wrong "walks down" PASS (the experimental limits above still apply); the clip is three frames about half a second apart, so it shows the failure moment, not what the game did in between.
- **Not tested:** cutting from a real screen-recorder file (only ffmpeg-generated test videos); recordings with variable frame rate, rotation or no duration; a Hermes session or the approval card for `playtest_clips`; any other game; Windows, macOS, Wayland-only; ffmpeg builds without libx264. Runs saved before 0.3.2 have no frame times and cannot be clipped. A recording whose start time is off gives a wrong moment.

## 0.3.0 (ModLab part) - scan, ask, never pick; and ModLab can no longer fill a disk (2026-11-12)

- Disk safety (a lab is a full copy of a game): ModLab now checks free space and its own total cap before writing every file, stops and removes its own partial work if a copy would pass the reserve (10 GB or 10 percent of the disk, whichever is larger) or the cap (default 25 GB), uses copy-on-write clones where the filesystem supports them (not on ext4, which this machine uses), keeps only the last 2 revisions of a lab, prunes toolkit output to 20 runs / 64 MB, removes unfinished lab folders left by a crash, and adds `modlab_cleanup` (report; dry-run-first deletion; only inside ModLab's own folder; only with confirm=true). Before this change every apply copied the whole game again, every revision was kept forever and the only guard was "free space at least twice the game". Settings: `modlab_max_total_gb`, `modlab_min_free_gb`, `modlab_keep_revisions`. A test fails the build if the shipped plugin grows big files or archives.
- New `modlab_setup`: scans the computer (installed modding tools, installed Steam games with duplicates, runtime components and unmounted libraries handled), identifies the engine and any anti-cheat of a chosen game folder by file signatures, lists the modding routes found for that engine with what each needs and what is missing, asks the user, and saves the route the user picked. ModLab never picks a route. `modlab_toolkit` and `modlab_create` return the interview until it is answered.
- New wiki `llmwiki/modding-routes.md` and `modding_catalog.json`: 12 engines, 18 routes, 39 tools, anti-cheat statements and upload rules, each with source and date (read 2026-11-12); RPG Maker, Creation Kit and several signatures are marked UNVERIFIED or "convention". Knowledge freshness: stale after 30 days or a passed deadline, and the plugin offers online research only if the user says yes; approved research is stored as dated overrides.
- Tested here: 121 Python tests. The engine scan was run on a real Steam library of 20 games on this machine and corrected three times from the result (nested game folders, Source 2 two levels deep, Godot with an embedded pack). Not tested: the game-folder scan on Windows or macOS, any loader install, or any mod run.
